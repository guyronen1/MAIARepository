  **Root cause (verified in code):** `ScanType` lives at *both* levels and they conflict. `MonitoredJob.ScanTypeId` makes the worker pick exactly one strategy (`strategies.FirstOrDefault(s => s.ScanType == job.ScanType)`), but `ScanCheckRule.CheckType` is *already* a per-rule discriminator and every strategy already filters the job's rules by it (`FileSystem`→`ErrorKeyword`, `Database`→`ColumnRange`/`ValueEquals`, `ApiEndpoint`→`StatusCode`/`ResponseContains`, `FileContent`→`FileContent`). # Full-codebase audit — gaps and problems, ranked (2026-07-08)

Findings from a docs-vs-code + architecture audit of both `Maia.Services` and `Maia.Client`. Doc accuracy verdict: MD files are highly accurate; the items below are the residual gaps. Items already tracked above are cross-referenced, not restated.

**🔴 1. Second-order SQL injection in the fix path — RESOLVED 2026-07-17.** Was: `SqlScriptExecutor.cs:74` substituted `{sourceId}`/`{referenceId}` into the SQL as a **plain string** (`PlaceholderResolver` did text `Replace`, no parameterization) then ran `new SqlCommand(sql, conn)` with **no parameters**. The ScriptDom write-guard (`SqlFixScopeValidator`) validates the placeholder is *positioned* inside the WHERE — it did not defend the *value*. `SourceId` originates from scanned data, so a row whose id is `' OR '1'='1` turned a scoped `WHERE id='{sourceId}'` into a bulk mutation under a write-capable login. **Fix (parameterized, not escaped):** new `IPlaceholderResolver.ResolveSqlAsync` → `ParameterizedSql` (rewritten SQL + `@pN` values). Every recognised `{token}` becomes a `@pN` marker and its value is bound as a `SqlParameter`; scanned data never becomes SQL text. Operator's quoted `'{sourceId}'` (and the UI helper's appended `= '{sourceId}'`) collapse to a bare `@p0` (matched quote-pair consumed); lone/embedded quotes degrade to an inert literal (0 rows), never inject or unbalance. Composite SqlScript steps route through the same `SqlScriptExecutor`, so they're covered too. `StoredProcedureExecutor` was already parameterized (`@FailureId` only, no template interpolation); `DbFixHandler` is a no-op stub. The write-guard now defends *position*, parameterization defends *value* — both required. 7 new tests in `PlaceholderResolverTests` (incl. the `' OR '1'='1` regression). **🔴 2. ## "Start from now" watermark seeding on new scan rules / sources — SHIPPED 2026-10-12 (opened the same day)

**Status:** built + verified end-to-end the same day (backend seeder, controller flag, both drawers, 16 unit tests; manual acceptance in the "Verified" note at the end of this section). Full rationale in `DECISIONS.md` → "Start scanning from now". The original spec follows unchanged for the record; **open follow-ons** from it: reset-watermark action, configurable look-back, show current watermark in UI. (Seeding on `PUT` and the checkbox on FS / FileContent *rules* were added the same day after the operator couldn't find the DB-only, create-only first cut.) **Hint-text pass:** all scan-rule drawer hints were shortened with the long copy on hover — except the new Composite-conditions "All lines are ANDed…" hint, which belongs to the in-flight conditions work and was left as written; give it the same short-line + ⓘ treatment when that feature settles.

**Problem.** A freshly created scan rule (DB) or scan source (FileSystem / FileContent) has **no watermark row**, so the first scan processes **everything that exists**: every table row that matches the rule filter, every byte of every matching log file, every content file in the folder. On large tables / long-lived logs this first tick is heavy, slow (can hit the per-`ScanType` lease timeout), and usually unwanted — the operator typically cares about failures *from now on*, not a historical backlog that may already be handled. Today the only workaround is to let the flood happen or to hand-insert a watermark row in SQL.

**Where the "scan everything" behaviour comes from (verified 2026-10-12):**
- **DB (`DatabaseScanStrategy`)** — `watermarks.GetDbWatermarkAsync(rule.CheckRuleId)` returns `null` for a new rule → `QueryMatchingRowsAsync` builds no `WatermarkColumn > @wm` filter → full matching set returned. Only applies to table rules (`ColumnRange` / `ValueEquals`) with a `WatermarkColumn`; `SqlQuery` rules run in-memory on whatever the operator's query returns (no watermark push-down).
- **FS keyword (`FileSystemScanStrategy.ReadNewContentAsync`)** — `GetFileOffsetAsync` returns `0` for an unseen file → `stream.Seek(0)` → whole file read and every historical error line becomes a `JobFailure` (capped 100 per keyword per scan, but still N files × 100).
- **FileContent (`FileContentScanStrategy`)** — `GetContentWatermarkAsync` returns `null` → the `mtime <= lastModified` skip never fires → every file in the folder is extracted.

**Proposed change — a checkbox, "Start scanning from now", **checked by default** (decided 2026-10-12: the safe/expected default for a new rule is "only new data"; the operator unticks it when they deliberately want the historical backlog):**

| Scan kind | Where the checkbox lives | What "now" seeds |
|---|---|---|
| DB table rule (`ColumnRange` / `ValueEquals` with `WatermarkColumn`) | **Scan-rule drawer** (`scan-rule-drawer.component.ts`), shown only when `WatermarkColumn` is set | Insert a `ScanDbWatermarks` row for the new `CheckRuleId`. Value = the current **max of `WatermarkColumn` over rule-filtered rows** (reuse `QueryFilteredMaxAsync`), NOT the wall-clock — `WatermarkColumn` may be an integer ID or a datetime in the *source* DB's clock, so a literal `DateTime.Now` string is wrong for IDs and racy for datetimes. If the filtered MAX is `null` (empty table) seed nothing — the first scan is then trivially cheap anyway. |
| FileSystem source (keyword mode) | **Scan-source drawer** (`scan-source-drawer.component.ts`) for `ScanType = FileSystem` | For every file currently matching `LogFolder` + `SearchPatterns` (+ `IncludeSubfolders`), upsert a `ScanFileWatermarks` row with `ByteOffset = current file length`. Files created later start at offset 0 as today (they are genuinely new). |
| FileContent source | Same drawer, `ScanType = FileContent` | For every currently matching file, upsert a `ScanContentWatermarks` row with the file's current `LastWriteTime` so only files modified after save are extracted. |
| ApiEndpoint | n/a | No watermark concept; checkbox hidden. |
| `SqlQuery` DB rule | n/a | No watermark push-down; checkbox hidden (or disabled with hint "SqlQuery rules have no watermark"). |

**Semantics to lock down before coding:**
- The checkbox is a **one-shot action at save time**, not a persisted setting — it seeds watermark rows and is then meaningless. Don't add a `StartFromNow` column to `ScanCheckRules` / `ScanSources`; carry it as a request-body flag (`seedWatermarkFromNow: bool`, **UI default `true`**; the backend treats a missing flag as `false` so existing API callers / scripts keep today's full-history behaviour) on `POST` (and arguably on `PUT` when `WatermarkColumn` / `LogFolder` / `SearchPatterns` changed and no watermark exists yet). Audit it: include `SeedWatermarkFromNow=true` in the Create/Update `AuditLog.Detail` so the "why did we never see rows before X" question is answerable later.
